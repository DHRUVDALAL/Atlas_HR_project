**Date:** July 13, 2026

## 1. Design Principles

### Conventions (Following Existing Patterns)
- **Primary Keys:** UUID with `uuid_generate_v4()` default
- **Foreign Keys:** UUID referencing parent table with `ON DELETE CASCADE`
- **Timestamps:** `TIMESTAMPTZ` with `DEFAULT NOW()`
- **Status Fields:** VARCHAR(20) with uppercase values
- **Audit Columns:** `created_at`, `updated_at`, `created_by`
- **Soft Delete:** Not implemented (existing tables use hard delete)
- **Indexes:** On foreign keys and frequently queried columns

### Naming Conventions
- **Tables:** snake_case, plural (e.g., `offers`, `onboarding`)
- **Columns:** snake_case (e.g., `offer_id`, `candidate_id`)
- **Indexes:** `ix_<table>_<column>` (e.g., `ix_offers_candidate_id`)
- **Foreign Keys:** `fk_<table>_<column>` (auto-generated by SQLAlchemy)

## 3. Detailed Table Definitions

### 3.1 offers Table

```sql
CREATE TABLE offers (
    offer_id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    candidate_id UUID NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',
    offered_ctc NUMERIC(12,2),
    joining_date DATE,
    approved_by VARCHAR(100),
    sent_at TIMESTAMPTZ,
    responded_at TIMESTAMPTZ,
    notes TEXT,
    created_by VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Indexes
CREATE INDEX ix_offers_candidate_id ON offers(candidate_id);
CREATE INDEX ix_offers_status ON offers(status);
CREATE INDEX ix_offers_created_at ON offers(created_at DESC);

-- Foreign Key
ALTER TABLE offers ADD CONSTRAINT fk_offers_candidate
    FOREIGN KEY (candidate_id) REFERENCES candidates(candidate_id) ON DELETE CASCADE;

-- Check Constraints
ALTER TABLE offers ADD CONSTRAINT ck_offers_status
    CHECK (status IN ('DRAFT', 'SENT', 'ACCEPTED', 'DECLINED'));

ALTER TABLE offers ADD CONSTRAINT ck_offered_ctc_positive
    CHECK (offered_ctc IS NULL OR offered_ctc > 0);
```

## 5. Migration Strategy

### Upgrade Steps
1. Create new tables in order (offers → offer_documents → offer_history → onboarding → document_verification → background_verification → asset_allocation → employee_checklist → onboarding_activity)
2. Add foreign key constraints
3. Add check constraints
4. Create indexes
5. Insert new permissions
6. Update role-permission mappings

### Downgrade Steps
1. Remove role-permission mappings
2. Remove new permissions
3. Drop new tables in reverse order
4. Verify existing tables unchanged

## 6. Data Integrity Rules

### Offer Rules
1. One offer per candidate (UNIQUE constraint on candidate_id)
2. Offer status must be valid enum value
3. Offered CTC must be positive (if provided)
4. Joining date must be in the future (application-level check)

### Onboarding Rules
1. One onboarding record per candidate (UNIQUE constraint on candidate_id)
2. Onboarding can only start after offer is accepted (application-level check)
3. Document verification types must be valid enum values
4. Background verification categories must be valid enum values
5. Asset types must be valid enum values
6. Checklist items must be valid enum values

### Cascade Rules
1. Deleting a candidate cascades to offers and onboarding
2. Deleting an offer cascades to offer_documents and offer_history
3. Deleting an onboarding cascades to document_verification, background_verification, asset_allocation, employee_checklist, and onboarding_activity

## 7. Performance Considerations

### Indexes
- All foreign keys indexed
- Status columns indexed for filtering
- Created_at indexed for sorting
- Composite unique constraints indexed

### Query Optimization
- Use `SELECTIN` loading for relationships (existing pattern)
- Paginate list queries with `LIMIT` and `OFFSET`
- Use `COUNT()` for total count before pagination
